# In-Process Runtime Proposal

The proposal is to move `pi-fork` from “subprocess Pi runner” to “in-process Pi `AgentSession` runner” while preserving the exact branch-entry snapshot semantics. The core shape should be: keep building the same JSONL snapshot from `ctx.sessionManager.getHeader()` plus `ctx.sessionManager.getBranch()`, write it to a temporary `fork.jsonl`, open that file in-process with Pi’s `SessionManager.open(...)`, create an `AgentSession` with that manager, load/filter extensions and tools through Pi APIs, run `session.prompt(buildForkTaskPrompt(task))`, and keep returning the same `ForkResult` shape used by rendering/cost today. This removes process startup, CLI argument translation, and stdout JSON parsing, but does not transform parent context into text or resolved messages.

The session plan is deliberately conservative because raw branch entries must remain exact. We should not seed the child from `buildSessionContext()` and should not use Tintin’s parent-context-as-text strategy. Both transform the source session. Instead, `buildForkSessionSnapshotJsonl` should remain the conceptual source of truth: header first, then every raw entry on the active parent branch, root-to-leaf, with no `pi-fork` type filtering. The first in-process version should write that exact JSONL to a temp dir, then use `SessionManager.open(tempPath, tmpDir, cwd)` so Pi loads, migrates, indexes, and interprets the session exactly as it would for `--session`. A tempting alternative is `SessionManager.inMemory(cwd).setSessionFile(tempPath)`, which loads exact entries into a non-persisted manager, but `getSessionFile()` still points at the temp file and extension behavior around that may be less predictable. For v1, use `SessionManager.open`; it is closest to current subprocess behavior. We can later experiment with `inMemory().setSessionFile(...)` if avoiding child writes to the temp file matters.

The architecture should introduce a runtime boundary instead of rewriting everything in place. Keep `buildForkTaskPrompt` and the `ForkResult`/render/cost contracts unchanged. Move or wrap the current subprocess implementation as a fallback runner, and add a new `runForkInProcess` path. The public tool flow in `src/index.ts` should still load config, resolve effort, build the exact snapshot, and call a runner, but the runner should be selected by config: `runtime: "auto" | "in-process" | "subprocess"`. During rollout, default to `auto`; eventually `auto` can prefer in-process unless config requires subprocess behavior. This lets users opt out quickly and lets us keep exact env/offline behavior available.

The in-process runner should roughly do this: create a temp dir and write the exact snapshot as `fork.jsonl`; open it with `SessionManager.open(tempPath, tempDir, cwd)`; construct `SettingsManager` and `DefaultResourceLoader`; create an agent session with `createAgentSession({ cwd, agentDir, sessionManager, settingsManager, modelRegistry: ctx.modelRegistry, model, thinkingLevel, resourceLoader })`; bind extensions; apply tool filtering; subscribe to session events; call `session.prompt(buildForkTaskPrompt(task))`; normalize the accumulated `ForkResult`; then unsubscribe, dispose the session, and clean up the temp dir in `finally`. The existing `processPiEvent` from `runner-events.js` should be reused directly if `AgentSession.subscribe(...)` emits compatible events, which it should based on Pi’s SDK and Tintin. This preserves activity, usage, retry metadata, thinking metadata, final assistant output, and nested fork usage without parsing JSON stdout.

Extension loading should preserve the current `pi-fork.extensions` tri-state exactly, but map it to `DefaultResourceLoader` rather than CLI flags. `extensions: null` means normal Pi extension discovery. `extensions: []` means no extensions. `extensions: ["./x.ts"]` means disable normal discovery and load only those explicit extensions. The mapping should be `noExtensions: config.extensions !== null` and `additionalExtensionPaths: config.extensions ?? []`. Do not copy Tintin’s default suppression of context files, skills, prompt templates, or system prompt files; `pi-fork` is meant to behave like the same Pi agent continuing work, not a named specialized subagent. If we later need tighter isolation, add explicit config for disabling skills/context files, but do not silently change the default agent environment.

Tool filtering should be explicit and exact-name based. Extension loading decides what extension code runs; tool filtering decides what the model may call. Those are different safety boundaries. After extension binding has registered tools, inspect `session.getActiveToolNames()` and `session.getAllTools()`, compute the allowed active set, then call `session.setActiveToolsByName(nextNames)`. The policy should support `tools?: string[] | null`, `deniedTools?: string[]`, and `allowRecursiveFork?: boolean`. `tools` omitted or `null` keeps Pi defaults. `tools: []` disables all tools. `tools: ["read", "bash"]` is an exact allowlist. `deniedTools` removes tools after default/allowlist selection. Unknown requested tools should produce a warning in result details rather than being silently trusted. Avoid Tintin-style fuzzy matching like `startsWith` or `includes`; package names, extension paths, and tool names are not reliable namespaces.

Recursive `fork` should be opt-in for the in-process runtime. In subprocess mode, recursion has an OS process boundary; in-process recursion shares memory, event loop, extension module state, model registry, and cancellation surface. The default should be `allowRecursiveFork: false`, which removes the `fork` tool from the child active tools if it is loaded. Users who deliberately want recursive delegation can set `allowRecursiveFork: true`. This should be tested because extension loading and tool filtering are separate: `extensions: null` may load `pi-fork`, but active tool policy should still hide `fork` unless recursion is explicitly enabled.

Effort profiles should stop being CLI flags in the in-process path and become direct model/thinking selection. Today subprocess mode appends `--provider`, `--model`, and `--thinking`. In-process mode should resolve the configured effort profile through `ctx.modelRegistry`; if the model exists, pass it and the thinking level to `createAgentSession` or the appropriate session/model API. If the configured profile cannot be resolved, fail loudly or return a clear warning depending on current effort behavior, but do not silently run the wrong model while reporting that `deep` or `fast` was selected. If no effort profile is configured, let the loaded session/Pi defaults determine model and thinking as they do today.

The biggest compatibility caveat is `environment` and `offline`. The current subprocess runner can build a per-child env with `buildChildEnv(...)`, force or remove `PI_OFFLINE`, and isolate that to the spawned process. In-process mode cannot safely mutate `process.env` around a run, especially with parallel forks. The proposal should explicitly treat per-child environment/offline as subprocess-only unless Pi exposes a safe per-session equivalent. In `runtime: "auto"`, if `config.environment` is non-empty or the requested `offline` behavior cannot be represented safely in-process, select the subprocess runner. In `runtime: "in-process"`, either return a clear warning/error for unsupported env/offline isolation or document that those settings are ignored in-process. Do not fake it.

Result compatibility is the migration boundary. `src/render.ts`, `src/cost.ts`, and parent tool responses should not care whether the runner was subprocess or in-process. `runForkInProcess` should still populate `ForkResult.task`, `exitCode`, `messages`, `stderr`, `usage`, `provider`, `model`, `stopReason`, `errorMessage`, `sawAgentEnd`, `effort`, `retry`, `thinking`, `activities`, and `toolExecutions`. Since there is no process exit code, use `0` for normal completion, `1` for thrown errors, and `130` for aborts unless semantic completion occurred. Existing `normalizeCompletedResult` and `isResultSuccess` semantics should be reused as much as possible.

Cancellation should use `session.abort()`, not process killing. Register the incoming `AbortSignal` before prompting, set a local `wasAborted` flag, call `session.abort()` on abort, and always remove the listener in `finally`. The runner must always unsubscribe from events, dispose the session, and delete the temp dir after the session is fully done. If `SessionManager.open` appends child entries to the temp file, that is fine; the file exists only for the duration of the in-process run and should be cleaned just like today’s snapshot file.

The implementation should be phased. Phase one adds config parsing for `runtime`, `tools`, `deniedTools`, and `allowRecursiveFork`, plus tests, with no behavior change. Phase two extracts the current subprocess runner behind a `runForkSubprocess` boundary and adds a runtime dispatcher. Phase three implements `runForkInProcess` using exact temp JSONL + `SessionManager.open`, direct `AgentSession` events, prompt execution, cancellation, and cleanup. Phase four adds extension loader mapping and exact tool filtering. Phase five makes `auto` prefer in-process except for env/offline fallback cases. Only after manual and automated validation should `auto` become the default documented path.

The test plan should prove the invariants that matter, not just the happy path. Session tests should assert that the snapshot still serializes raw `getHeader()` + `getBranch()` entries and that the in-process runner opens that exact JSONL rather than replaying transformed messages. Runtime tests should fake or stub `AgentSession` events and verify `ForkResult` fields, usage, final output, retry state, thinking/activity tracking, abort behavior, dispose cleanup, and error normalization. Extension tests should cover `extensions: null`, `[]`, and explicit arrays mapping to loader options. Tool-policy tests should cover defaults, `tools: []`, exact allowlists, denied tools, unknown tool warnings, and recursive fork disabled/enabled. Compatibility tests should assert `runtime: "auto"` falls back to subprocess when env/offline isolation is required.

The main tradeoff we intentionally accept is that in-process execution is not the same isolation model as a subprocess. It is faster, easier to control, and gives structured events directly, but extension code shares the process and can share global state. That is why subprocess fallback should remain durable, not just temporary. The user-facing promise should be: in-process is the fast/default runner for normal forks; subprocess remains available for strict isolation, per-child env/offline behavior, and debugging. The most important constraint — exact branch entries — is preserved by keeping the JSONL snapshot and loading it with Pi’s own session loader instead of transforming it.
